
# 外送系統：完整解析

## 一、專案本質

這是雲端運算課程作業：用同一份程式、同樣規格的兩套 Cloud Run 部署，對照「固定容量」與「自動擴展」在流量暴增時的差異。重點不在外送業務本身，而在於**製造一個可重現、可觀察的過載場景**。

核心論述鏈：

1. 外送流量集中在尖峰，且每筆訂單都要即時運算。
2. 固定版（max 1）運算能力有上限，超載後請求排隊、逾時。
3. 擴展版（max 8）依負載增加 instance，仍可正常回應。
4. 控制變因：同一映像檔、同 CPU/記憶體/concurrency，唯一差別是 max-instances。

## 二、系統架構

| 元件               | 角色                       | 關鍵約束                            |
| ---------------- | ------------------------ | ------------------------------- |
| `web`            | 提供頁面、地圖、設定；收集回報；SSE 推送指標 | 必須單 process、單 instance（指標只在記憶體） |
| `dispatch-fixed` | 派單與追蹤運算（對照組）             | max 1                           |
| `dispatch-auto`  | 同上（實驗組）                  | max 8                           |
| 前端               | 手機點餐、追蹤、Debug 儀表板        | 純 HTML/CSS/JS、SVG 自繪，無 CDN      |
| `loadtest`       | 另一台電腦模擬大量顧客              | 開放式負載，直接打 dispatch              |

資料流重點：手機**直接**呼叫兩個 dispatch（量到真實延遲），頁面由 web 提供（壓測時頁面仍能開），結果再回報給 web 彙整。

## 三、關鍵設計決策與其理由

**1. dispatch 完全無狀態**  
追蹤狀態（`tracking` dict）由用戶端保管，每次 `POST /api/track` 帶回。理由：擴展版 instance 會增減，若狀態存在記憶體，請求換到另一台就失效；又不能用資料庫（規則 2）。代價：狀態未簽章可竄改，已列入已知限制。對應的驗證：兩個獨立程序交替處理同一配送，結果須與單程序相同。

**2. 追蹤機制是負載的主要來源**  
派單一次約 55 ms；追蹤每次約 10 ms，但一筆配送約追蹤 40 次，總量約為派單的 7 倍。這讓「進行中的配送」成為持續負載，也讓擴展版的 instance 在配送結束前不會立刻縮掉。

**3. 時間模型**  
模擬時間 = 真實秒數 × `TIME_SCALE`（預設 20）。以 dispatch 伺服器時鐘為準，與用戶端無關。追蹤推進以「模擬時刻」計算路況，所以配送中路況會變、路線會重新規劃。要求：不同呼叫間隔下，送達模擬時間差不超過 5%。

**4. 開放式負載**  
新顧客依固定到達速率出現，不等前一位完成。封閉式負載會因目標變慢而自動降速，掩蓋固定版的瓶頸。多程序壓測避免單一 Python 程序的事件迴圈成為瓶頸，污染延遲量測。

**5. 刻意不做防護**  
無速率限制、IP 封鎖、驗證。目的是讓壓測流量全進後端。

## 四、演算法層

**城市路網（4.1）**：由固定種子產生，三個服務結果一致。N×N 格狀、約 10% 路段封閉但保持連通（BFS 驗證）、主幹道 15 秒/一般 30 秒、河流只能從主幹道橋過、6 家店各 4–6 項餐點。地址以 SHA-256 對應路口。

**派單（4.2）**：

1. 路況係數 1.0–2.0（依分鐘與路段，不可快取）
2. 隨機產生 `RIDERS` 位外送員
3. 自店家做一次完整 Dijkstra，取最近 `CANDIDATES` 位
4. 懲罰法求替代路線（每條路線的邊權重乘 `ALT_PENALTY` 後重搜）
5. 評分 = 最佳 ETA + 0.5 × (最差替代 ETA − 最佳 ETA)，取最低
6. 行程：抵店 → 等備餐 → 送餐

搜尋次數 ≈ `1 + (CANDIDATES+1) × ALT_ROUTES` = 1 + 6×3 = 19 次，這是調整單筆運算量的主旋鈕。

**追蹤（4.3）**：路段中途不迴轉，先走完再重新規劃；用點對點 Dijkstra（目標出列即停）降低成本；ETA = 剩餘路線時間（+等待+送餐路線）。

## 五、API 與指標

- dispatch：`POST /api/orders`、`POST /api/track`、`GET /api/healthz`。CPU 密集端點一律 `def`（讓 FastAPI 丟執行緒池，不阻塞 event loop）。
- web：`/api/config`、`/api/map`、三種 report、`/api/stream`（SSE）。
- outcome 統一定義：ok / timeout（>10s）/ busy（429）/ error。
- 指標用 600 格環狀陣列，以 **web 收到時間**分格，不信任回報方時戳。成功率取「最近有完成請求的那一秒」，避免服務掛掉後被 60 秒視窗撐住，這個細節很有設計感。

## 八、風險與需要驗證的地方

1. **容量 C 可能偏低**。以 README 的數字估：單位顧客 CPU ≈ 55 + 40×10 ≈ 455 ms，1 vCPU 理論約 2.2 位新顧客/秒；但規劃書 P8 要求 C 在 5–15 rps。落差的原因可能是「rps」指請求而非顧客（請求數 = 1 + 40 次/顧客），或 `TIME_SCALE`、備餐時間會改變追蹤次數。**這需要先釐清 C 的單位**，否則 P8 的校準目標會自相矛盾。
2. **擴展版餘裕不足**。R = 5C、max 8 台，理論利用率約 62%，但 Cloud Run 冷啟動、concurrency=4 排隊、擴展延遲都會吃掉餘裕。
3. **夥伴近期變更改變了負載模型**：備餐時間縮短（追蹤次數減少）、離開頁面放棄追蹤（觀眾端負載提早消失）。README 4.3 的「約 40 次、7 倍」需重新量測。
4. **規劃書殘留錯誤**：P3 的 `hub.main:app` 應為 `web.main:app`；P1 沒提河流但 README 有。
5. **Python 版本分歧**：容器 3.12，本機相容 3.10，需避免 3.11+ 語法。
6. **min-instances 衝突**：`deploy` 與 `warm`/`cool` 都會動 min-instances，需確認 `deploy` 不覆蓋展示前的 warm 狀態。
7. **免費額度**：Cloud Run、Cloud Build、Artifact Registry 的免費額度要部署前確認；壓測必須指定 `--duration`，舊映像檔要清理。
